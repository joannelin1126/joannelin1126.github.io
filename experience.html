03 PIF Automation

The challenge

One PIF. Multiple SKUs. Parallel Dependencies.

The hardest problem was not storing statuses. It was translating SKU-level progress into a reliable PIF-level launch forecast.

01 / Process discoveryAligned with Operations and NPD to map stages, responsible owners, handoffs, prerequisites and standard lead times.
02 / Many-to-oneOne PIF may include multiple SKUs, each with a different completion state. A PIF cannot be read from one SKU alone.
03 / Parallel executionIndependent workstreams can run together; downstream milestones depend on all required branches being ready.
Core design problem: many SKUs × concurrent tasks × different lead times × one PIF deadline

Business analysis

Before VBA: Define the Real Workflow

Worked with Operations and NPD to clarify which tasks were sequential, which could run simultaneously, and what constituted PIF readiness.

01 DiscoverMap required documentation and ownership
02 ValidateConfirm lead times, dependencies, exceptions
03 ModelSet SKU-to-PIF aggregation and project deadline logic
04 AlignReview proposed tracking rules with stakeholders

Value of collaboration: prevented a misleading linear tracker by confirming real operational dependencies.

Forecast design

Forecasting Depends on the Slowest Required Path

Illustrative scenario: three parallel workstreams start together and must finish before a final step can begin.

Branch B
7 days
Branch C
14 days
Branch D
9 days
Parallel block duration = MAX(7, 14, 9) = 14 days → + final dependent step

Not 7 + 14 + 9. At the SKU level, each eligible branch must be tracked and then reconciled at PIF level.
